# swath agent guide

Read this before changing swath. General contribution rules are in
[`CONTRIBUTING.md`](CONTRIBUTING.md).

## What swath is

swath is a command-line tool for parallel listing and inventory of large object stores
and filesystems. The unreleased Go implementation on `main` supports local and mounted
filesystems, S3, GCS and Azure Blob flat namespaces, with size summaries and sorted
Parquet output. The latest published release is the S3-focused Java v0.3.2. Go will
replace Java at release; this repository still contains both implementations.

Start with [`README.md`](README.md) and the [Go guide](go/docs/getting-started.md). The
[visual field guide](https://swath.varve.io/field-guide/) is historical Java v0.3.2
documentation, not the Go algorithm.

## Sources of truth

- Product positioning and release status belong in `README.md`. Go behavior belongs in
  `go/docs/`; root `docs/` usage and engine pages describe the Java release.
- [`go/docs/internals/contracts.md`](go/docs/internals/contracts.md#the-invariants-i1i12)
  owns the load-bearing invariants I1–I12 and the dataset, producer and recovery rules;
  [`go/docs/dataset.md`](go/docs/dataset.md) owns the dataset profile and schemas.
- [`go/docs/internals/range-engine.md`](go/docs/internals/range-engine.md) owns the Go
  listing algorithm and [`go/docs/internals/architecture.md`](go/docs/internals/architecture.md)
  maps it to packages and runtime flow. The root `docs/internals/` pages (contracts,
  algorithms, architecture) describe the Java engine; do not copy their details into Go.
- CLI reference blocks (synopses, option lists, diagnostic options, log events, the run
  report's fields) are generated by tests in `go/`; regenerate with `UPDATE=1`, never by
  hand. `go test ./docs` checks every Markdown link under `go/`.
- Code is the final authority when a difference is found. Correct the documentation in
  the same change rather than adding a banner that leaves both versions in place.
- Visible options and defaults come from the CLI implementation and generated help.
  Narrative documentation teaches choices and exceptional constraints instead of
  maintaining another exhaustive option list.

Use [`docs/style.md`](docs/style.md) for public terminology, project casing, consistency
language, evidence claims, and documentation ownership.

## Correctness spine

The highest-risk areas are:

- byte-exact key ordering;
- range boundaries and the split/steal protocol;
- checkpoint and resume ordering;
- Parquet part durability and publication;
- cancellation and shutdown order; and
- concurrency changes that can create gaps, overlaps, deadlocks, or unbounded memory.

Changes to this spine need adversarial tests. A high-risk unit's no-gap/no-overlap,
mid-crash resume, or concurrency guard should be independently authored or reviewed when
possible. Test tiers are documented in
[`docs/ops/dev/TESTING.md`](docs/ops/dev/TESTING.md).

## Instrument algorithm changes

Every new algorithm path—pivot choice, split trigger, seed path, pacing gate, retry
branch, or router decision—must emit an engagement reason plus any cheap classification
signal it observes.

The test is practical: can a completed run report show whether the path engaged and what
constrained it? If not, the path is under-instrumented.

The contributor reference is
[`docs/internals/metrics-internals.md`](docs/internals/metrics-internals.md).

## Build and test

- `./gradlew build` is the integration gate.
- The Docker-free per-commit loop is `./gradlew build -PnoIntegration`.
- The root `:test` task does not exist. Scope filtered tests to a subproject, for example:

  ```bash
  ./gradlew :swath-core:test --tests 'io.varve.swath.SomeTest'
  ```

- Deep and performance tiers are opt-in. See
  [`docs/ops/dev/TESTING.md`](docs/ops/dev/TESTING.md).
- Read [`docs/ops/dev/CI.md`](docs/ops/dev/CI.md) before changing CI: the workflows, the
  `ci-gate` check and the reasoning behind them.
- Docker is available for Testcontainers, LocalStack, MinIO, and replay checks.
- Use DuckDB or the repository verifier for Parquet output.

## The Go tree

- The Go implementation lives in [`go/`](go/): module `github.com/varveio/swath/go`, command
  `go/cmd/swath`, packages under `go/internal/`. Its launcher and dataset differ from the
  current Java release; Go replaces Java at release rather than becoming a second edition.
- [`go/docs/`](go/docs/) is the source of truth for the Go code (architecture, the invariants,
  ordering, Parquet output, providers, testing, CLI); a change to `go/` is not done until its
  page there is current. Measurements are recorded, dated, in
  [`go/docs/internals/measurements.md`](go/docs/internals/measurements.md).
- A provider's runtime integration is its directory under `go/internal/source/` plus one blank
  import in `go/cmd/swath`; reader contracts, verifier support and central conformance tests
  still need explicit integration. Follow the verified
  [provider checklist](go/docs/internals/providers.md#adding-a-provider). Providers compose
  shared flag groups, the range engine and `keyrange.Registered`, `objhttp` client plumbing
  and schema helpers; credential, endpoint, identity and wire policies stay provider-owned.
  The internal owners are [clients](go/docs/internals/clients.md),
  [restart](go/docs/internals/range-engine.md#resume),
  [schemas](go/docs/internals/parquet-output.md#schemas) and
  [spill codecs](go/docs/internals/ordering.md#payload-delta-codec).
- The gate is `cd go && go vet ./... && go test -race ./...`; CI runs it sharded. Locally
  run the tests you change, not the whole suite; repeats go through `go-stress.yml`. Static
  builds use `CGO_ENABLED=0`.
- A commit that touches `go/` needs its selected Go jobs of `ci.yml` green (`go-lint`, the `go-race`
  shards, `go-nonrace`, `go-build`, `go-xos`, `go-fixtures`; `ci-gate` requires them). Selection
  follows complete modules and their dependants; main validates all modules and publishes `go-full-gate`, which release requires at its exact SHA.
  [`go/docs/internals/testing.md`](go/docs/internals/testing.md) says what each job and tier runs and when.

## Repository discipline

- Use one integration branch per effort and one pull request to `main`.
- Keep commits focused and signed off.
- Never commit directly to `main`, merge a pull request, force-push shared work, commit
  secrets, or delete outside build and scratch directories.
- Never commit a red build.
- Reuse existing helpers, registries, and dependencies instead of creating another source
  of truth.
- Avoid magic strings, telescoping constructors, and abstractions introduced only to
  narrate a small change.
- Add options, comments, metrics, or documentation only when they clarify a behavior the
  code actually supports.
